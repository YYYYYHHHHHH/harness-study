# 代码规范审查

## 范围与原则

- 默认只审查，不修改文件、不暂存、不提交。用户明确要求修复时再做最小范围修改。
- 优先遵循仓库的 AGENTS.md、贡献指南、现有代码风格及 lint、formatter、TypeScript 配置，不强行引入个人偏好或新的规范工具。
- 用户指定的文件、提交或分支优先；未指定时检查当前工作区的已暂存、未暂存及相关未跟踪代码。没有改动时说明情况并询问审查目标，不擅自审查整个仓库。

## 执行步骤

1. 确认工作目录和 Git 仓库，查看 `git status --short`、`git diff --stat`、`git diff`、`git diff --cached`。未跟踪文件不在 diff 中，按范围单独读取；大文件按需分段查看。
2. 阅读适用的项目约定、`package.json` 及相关配置，确认语言、检查脚本和测试方式。阅读变更文件的上下文、相关调用处及测试，避免只凭 diff 断章取义。
3. 检查代码规范：
   - 命名语义、目录组织、导入顺序、格式与现有代码是否一致。
   - 类型是否准确，是否存在无必要的 `any`、类型断言或忽略类型检查。
   - 职责是否清晰，是否存在重复实现、无用代码、过度抽象和不必要依赖。
   - 异步流程、错误处理、资源清理、参数校验和边界条件是否符合项目约定。
   - 注释与公开接口文档是否准确，配置、日志中是否意外暴露密钥或敏感数据；不要在报告中复制密钥。
   - 测试是否覆盖主要行为、失败分支和边界条件，是否产生兼容性或行为回归。
4. 若项目提供 lint、格式检查、类型检查、测试脚本，执行与改动相关的非自动修复检查。本仓库默认使用 `npm run check` 和 `npm test`。不要执行会改写文件的 `--fix` 或格式化命令；没有配置的检查明确标注未执行，不声称已通过。
5. 将工具结果与人工阅读结合，仅报告有依据、可定位且可操作的问题。区分规范违反、真实缺陷和可选建议，不把个人偏好当作阻塞项。

## 输出格式

- **结论**：是否发现需要修复的问题，以及本次审查范围。
- **问题列表**：按严重程度排序，每项包含 `[严重程度] 文件:行号 — 问题`、依据/影响和最小修复建议。严重程度使用「高」（安全风险、重大缺陷）、「中」（规范违反、维护或可靠性问题）、「低」（非阻塞建议）。
- **验证结果**：列出执行命令及通过/失败状态；未执行的检查及原因。
- **局限**：未覆盖的范围、缺失的上下文或环境限制。

没有发现问题时明确写「在本次审查范围内未发现问题」，但不要保证代码绝对无缺陷。
